- stage: planner / stage_n 1
- 기준 문서: `GAME_DESIGN.md` v0, `AGENTS.md`
- R1 goal (단 하나): **맵 위에서 캐릭터(반딧불이)가 한 칸 움직인다.**
- 저장소 현황(확인): `git ls-files` 결과 소스 파일 0개. `AGENTS.md`, `GAME_DESIGN.md`, `.gjc/**`만 존재. `src/`, `test/`, `index.html` 없음.

## Summary
R1은 "한 칸 이동" 하나만 만든다. `GAME_DESIGN.md` 2장(이동 규칙)은 숫자가 모두 있으므로 순수 로직과 테스트는 지금 바로 만들 수 있다. 그러나 5장(맵)과 6장(팔레트)이 비어 있어서 **맵 내용과 화면 렌더링은 R1 안에서 완성할 수 없다.** 따라서 R1을 R1a(로직+테스트, 지금 가능)와 R1b(맵+렌더+index.html, 5장·6장 확정 후)로 나누고, R1b는 사람 결정 대기 상태로 명시한다.

## 1. Principles
1. **기획서가 유일한 근거.** 2장 표의 숫자(격자 한 칸, 150 ms, 32 px, 512×384 = 16×12, 방향키 4개, 대각선 없음, 벽/화면 밖이면 제자리, 입력 무시 규칙)만 쓴다. 이 값들은 기획서에 "(에이전트 제안)"으로 표기되어 있고, 계획도 그 표기를 유지한다(사람 확정 필요).
2. **빈 장은 채우지 않는다.** 5장(맵), 6장(팔레트)은 비어 있다. 맵 문자, 레이아웃, 색 hex를 계획이나 코드가 임의로 정하지 않는다. 기획서를 먼저 고치고 사람에게 보여준다(`AGENTS.md` 금지 사항).
3. **로직과 화면 분리.** `src/logic.js`는 canvas를 모르고 상태를 받아 새 상태를 돌려주는 순수 함수만 둔다. 이동 규칙은 전부 여기에 있고, 렌더는 색이 확정된 뒤에 붙인다.
4. **테스트 기대값은 기획서 숫자에서 가져온다.** 코드가 하는 일을 베낀 테스트는 쓰지 않는다. 16×12 경계, 150 ms, 제자리 규칙, 입력 무시 규칙이 기대값의 출처다.
5. **완료는 사람이 브라우저에서 확인하는 것.** 테스트 통과는 완료가 아니다. 다만 9장 수용 기준이 R2 소관이라 R1은 2장 기반의 임시 확인 항목으로 사람 확인을 받는다.

## 2. Decision Drivers (top 3)
1. **5장 공백이 R1 goal의 "맵 위에서"를 막는다.** 맵 문자 규칙이 없으면 `src/levels.js`를 쓸 수 없고(좌표 직접 기재 금지), 벽 판정의 실제 데이터도 없다. → 로직은 맵을 인자로 받는 순수 함수로 두고, 맵 데이터 파일은 5장 확정 뒤로 미룬다.
2. **6장 공백이 렌더를 막는다.** 색은 6장 8색 hex만 허용. hex가 0개면 canvas에 그릴 수 있는 색이 없다. → index.html/렌더 코드는 6장 확정 뒤.
3. **9장 수용 기준이 R2 소관이다.** R1 완료 판정의 공식 근거가 아직 없다. → 2장 표 항목을 1:1로 대응시킨 "R1 임시 확인 목록"을 만들고, 9장이 채워질 때 이 목록을 9장 번호로 대체한다.

## 3. Viable Options
### Option A (권장) — R1a 로직+테스트 먼저, R1b 렌더는 5장·6장 확정 후
- 내용: `src/logic.js` + `test/`만 R1a에서 만든다. 맵은 함수 인자(그리드)로 받는다. `index.html`, `src/render.js`, `src/levels.js`, `src/sprites.js`, `src/strings.js`는 R1b.
- 장점: 기획서에 있는 2장 숫자만으로 진행 가능. 발명 0. 테스트로 즉시 검증 가능. 5장·6장이 확정되면 로직 수정 없이 데이터만 끼운다.
- 단점: R1 종료 시점에 사람이 브라우저에서 볼 화면이 없다 → `AGENTS.md` 완료 조건(사람이 브라우저 확인)을 R1a만으로는 만족하지 못한다. R1b가 사람 결정에 묶인다.

### Option B — 5장·6장 확정까지 R1 전체 보류
- 내용: 계획만 내고 코드 작업을 전혀 시작하지 않는다. 사람이 5장 맵 문자와 6장 8색 hex를 채운 뒤 R1을 한 번에 한다.
- 장점: goal 1개가 한 커밋에서 완결되고 사람 브라우저 확인까지 한 번에 끝난다. 재작업 위험 0.
- 단점: 사람 응답까지 진척 0. 2장은 이미 숫자가 다 있는데도 검증 가능한 작업을 놀린다.

### Option C (무효) — 임시 맵/임시 색으로 R1 전체 구현
- 무효 사유: `AGENTS.md` "기획서에 없는 기능/값을 만들지 않는다", "색은 6장 8색 hex만", "맵은 5장 문자 규칙을 그대로 복사"를 정면으로 위반한다. 또한 사용자 요청("기획서에 없는 것은 계획에 넣지 마라")에 반한다. 추가로 fixture 데이터 스크린샷은 증거가 아니라고 명시되어 있어 검증 가치도 없다.

**권고: Option A.** 단, R1b는 블로커 해소 전까지 착수하지 않는다. 사람이 "한 커밋 한 goal"을 더 중시하면 Option B로 전환한다(계획 변경 불필요, R1a를 보류하면 됨).

## 6. R1 수용 기준 (기획서 장 번호 대응)
### R1a — `node --test test/`로 검증 가능
- **AC-R1-1 (2장: 격자 한 칸 단위)** ↑↓←→ 각 1회 입력에 좌표가 정확히 1칸만 바뀐다. — test
- **AC-R1-2 (2장: 대각선 없음)** 두 방향 동시 입력이 대각선 이동을 만들지 않는다. — test
- **AC-R1-3 (2장: 화면 밖이면 제자리)** 16×12 그리드 경계(x 0/15, y 0/11)에서 밖으로 향한 입력은 좌표를 바꾸지 않는다. — test
- **AC-R1-4 (2장: 벽이면 제자리)** 대상 칸이 벽인 입력은 좌표를 바꾸지 않는다. — test (fixture 그리드)
- **AC-R1-5 (2장: 150 ms / 입력 무시)** 한 칸 이동 완료 전 입력은 무시되고, 150 ms 경과 후 다음 입력이 1칸 이동을 만든다. — test
- **AC-R1-6 (AGENTS.md 코드 규칙)** `src/logic.js`에 canvas/document/window 참조가 없다. — test 또는 소스 확인

### R1b — 사람이 `index.html`을 열어 확인 (5장·6장 확정 후에만 유효)
- **AC-R1-7 (2장: 화면 512×384, 타일 32 px)** canvas가 512×384이고 타일 격자가 16×12로 보인다.
- **AC-R1-8 (5장)** 레벨 1 맵이 5장 문자 그대로 그려진다.
- **AC-R1-9 (2장)** 방향키 1회에 반딧불이가 눈에 보이게 한 칸 움직이고, 벽/화면 끝에서는 움직이지 않는다.
- **AC-R1-10 (6장)** 쓰인 색이 6장 8색 hex 밖으로 나가지 않는다.

> 9장이 채워지면 AC-R1-* 번호를 9장 번호로 교체한다. 그때까지 R1 완료 선언은 "2장 기준 임시 확인"임을 밝혀야 한다.

## 7. Blockers / Open items (사람 결정 필요)
1. **5장 맵 — 비어 있음 (차단).** 맵 문자 규칙(어떤 문자가 벽/빈칸/시작 위치인지)과 레벨 1 맵 16×12 문자 그림이 없다. `AGENTS.md`는 5장 문자 규칙을 `src/levels.js`에 **그대로 복사**하라고 하고 좌표 별도 기재를 금지한다. **따라서 R1의 맵 내용은 5장 없이 완성할 수 없다.** 계획은 이 값을 발명하지 않는다.
2. **6장 팔레트 — 비어 있음 (차단).** 8색 hex가 없으면 `src/sprites.js` 팔레트 인덱스의 의미와 렌더 색이 정의되지 않는다. 임시 색 사용은 금지.
3. **9장 수용 기준 — 비어 있음, R2 소관.** R1의 공식 완료 판정 근거가 없다. 9장 없이 R1에서 확인 가능한 것: 2장 표의 7개 항목(격자 한 칸, 150 ms, 32 px, 512×384/16×12, 방향키 4개·대각선 없음, 벽·화면 밖 제자리, 입력 무시 규칙) — 전부 `test/`에서 숫자로 검증 가능하다. 확인 **불가능**한 것: 성공/실패 판정, 점수, 제한 시간, 레벨 전환 등 R1 범위 밖 항목. 즉 R1은 "2장 준수"까지만 증명하고 goal 완료는 사람 확인 + 9장 확정 후 재확인이 필요하다.
4. **4장 오브젝트 — 비어 있음(R1에서 채운다고 표기).** 반딧불이의 스프라이트 모양·크기가 정의되지 않아 R1b 렌더에 필요하다. 기획서 4장을 먼저 채워야 한다.
5. **2장 숫자의 "(에이전트 제안)" 표기.** 7개 값 모두 사람 확정 전이다. 코드/테스트에 들어가는 순간 고정되므로, 사람이 확정 또는 수정해야 한다. 수정 시 기획서를 먼저 고친다.

## Sequencing and dependencies
1. (사람) 2장 7개 값 확정 또는 수정 → 테스트 기대값 고정.
2. R1a: `src/logic.js` → `test/logic.test.js` → `node --test test/` 통과.

- 완료 보고 시 AC-R1-* 번호(9장 확정 후에는 9장 번호)로 "무엇을 열어 무엇을 보라"를 말한다.
- 커밋: `goal-1:` (goal 하나에 커밋 하나).

## Escalation / Risk Gate
- **즉시 에스컬레이션:** 구현 중 5장·6장 값을 추측하고 싶어지는 순간 멈추고 사람에게 묻는다. 같은 시도 6회 초과 금지(`AGENTS.md`).
- **게이트 1:** 5장·6장 공백 상태에서 R1b 파일을 만들려 하면 중단.
- **게이트 2:** 테스트 기대값이 2장 숫자로 역추적되지 않으면 그 테스트는 쓰지 않는다.
- **게이트 3:** 코드가 2장 숫자를 바꾸려 하면 기획서를 먼저 고치고 사람에게 보고.

## Risks and mitigations
| 위험 | 영향 | 완화 |
|------|------|------|
| 5장 맵 문자 규칙이 로직의 벽 표현과 다르게 확정됨 | `src/logic.js` 벽 판정 인터페이스 수정 | 로직은 "칸이 통행 가능한가"를 그리드 인자로만 묻게 설계. 문자 해석은 `src/levels.js`가 담당 |
| 2장 (에이전트 제안) 값이 사람 검토에서 바뀜 | 테스트 기대값 전부 수정 | 숫자를 테스트 상단 상수 한 곳에 모으고 출처를 2장으로 주석 |
| R1a만 끝내고 goal 완료로 오인 | 완료 조건 위반 | 완료 보고에 "브라우저 확인 미완, R1b는 5장·6장 대기"를 명시 |
| 150 ms 타이밍을 테스트에서 실시간 대기로 검증 | 느리고 불안정한 테스트 | 로직이 시간을 인자(now/dt)로 받게 하여 가짜 시간으로 검증 |
| 9장 공백으로 수용 기준이 계획자 창작이 됨 | 기준 불일치 | AC-R1-*을 2장 표 항목에 1:1 대응시키고, 9장 확정 시 교체를 전제로 표기 |

## Handoff
- **executor**: R1a(`src/logic.js` + `test/logic.test.js`)만. R1b는 할당하지 않는다.
- **사람(필수)**: 기획서 4장·5장·6장 작성, 2장 (에이전트 제안) 값 확정. 이것 없이는 R1 goal이 닫히지 않는다.
- **architect**: 불필요(파일 2개, 순수 함수).
- **critic**: 5장·6장 확정 후 R1b 착수 직전에 "발명한 값이 없는지" 1회 점검 권장.
