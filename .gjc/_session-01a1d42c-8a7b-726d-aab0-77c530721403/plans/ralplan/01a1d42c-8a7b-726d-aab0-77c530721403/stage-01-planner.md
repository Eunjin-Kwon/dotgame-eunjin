## RALPLAN-DR summary
모드: short (사전 부검 불필요 — 범위가 기획서에 의해 닫혀 있고 되돌리기 비용이 낮다).

### Principles
1. 기획서가 단일 진실이다. 코드·테스트의 모든 숫자는 GAME_DESIGN.md(= R2_decisions.md에서 옮겨 적은 값)에서 온다. 기획서에 없는 것은 만들지 않는다.
2. 규칙은 캔버스를 모르는 순수 함수(src/logic.js)에 둔다. 그려야만 검증되는 규칙을 만들지 않는다.
3. 완료는 테스트 통과가 아니라 9장 수용 기준 번호로 사람이 브라우저에서 확인하는 것이다.
4. 한 goal에 커밋 하나. 같은 시도를 6번 넘게 반복하지 않는다. 막히면 멈추고 사실대로 기록한다.
5. 미결정 사항은 추측해서 코드에 넣지 않고 Intent Reconciliation에 기본 제안과 함께 올린다.

### Decision Drivers (top 3)
1. **게이트 순서**: design-v2 커밋 전에는 코드를 고치지 않는다. 기획서가 흔들리면 테스트 기대값이 모두 흔들린다.
2. **순수 로직 경계**: 거미 순찰·접촉·타이머·점수·화면 상태는 전부 logic.js의 순수 함수여야 node --test로 검증 가능하다.
3. **값 보존**: 8개 / 300 ms / 60 s / 100점 / 10점 / 16×12 / 32 px / 8색은 사람이 확정한 값이며 코드가 바꿀 수 없다.

### Viable Options
**옵션 1 (채택) — 기획서 먼저, goal-2 → goal-3 순차**
- 장점: AGENTS.md 완료 조건과 일치. 수용 기준 번호가 goal 경계와 그대로 맞는다(6~17 / 18~26). 각 goal이 독립 커밋.
- 단점: goal-2 단계에서 실패/클리어가 화면 없이 "멈춤"으로만 보여서 사람 확인이 다소 밋밋하다(수용 기준 14·17이 "화면은 goal-3"으로 이미 그렇게 쓰여 있어 허용된다).

**옵션 2 — goal-2와 goal-3을 한 번에 구현**
- 장점: 화면 전환까지 한 번에 보여 사람 확인이 자연스럽다.
- 단점: 커밋 하나에 수용 기준 21개가 묶여 실패 시 원인 분리가 어렵다. "goal 하나에 커밋 하나" 규칙과 R2_decisions H절의 goal 두 개 지시에 어긋난다. → 기각.

**옵션 3 — 화면 상태를 main.js에 두고 logic.js는 이동만 유지**
- 장점: 변경 파일이 적다.
- 단점: 상태 전이·점수·타이머가 테스트 불가 영역(DOM/rAF)으로 들어간다. AGENTS.md의 logic.js 규칙과 "코드가 하는 일을 그대로 적은 테스트 금지" 규칙 둘 다 위반. → 기각.

### 규칙 (전부 기획서 값)
- 이슬방울 8개(확정). 반딧불이가 그 칸에 들어가면 사라지고 개수 +1. 이미 먹은 칸·빈 칸은 변화 없음(수용 9~11).
- 거미 1마리, 가로 왕복, **300 ms마다 한 칸**(확정), 다음 칸이 벽이면 반대 방향. 처음 방향 왼쪽. 이슬방울을 먹지 않고 지나가며 방울이 거미를 막지 않는다(수용 12·13).
- 접촉 = **같은 칸** 또는 **서로 자리 맞바꿈**. 반딧불이 이동 직후와 거미 이동 직후 각각 검사하고, 참이면 **즉시 정지**(수용 14·15). goal-2 단계에서는 화면 없이 정지만 한다(결과 화면은 goal-3).
- 제한 시간 60초(확정), 1초씩 감소, 0에서 정지(수용 16·17).
- 타이머·거미 시작 시점: 타이틀에서 Enter로 플레이에 들어가는 순간(에이전트 제안 — Intent Reconciliation 참조). goal-2 단계에서 타이틀이 아직 없다면 페이지 로드 = 플레이 시작으로 간주하고 goal-3에서 Enter로 옮긴다.
- 모든 규칙은 src/logic.js의 순수 함수. 캔버스·DOM·performance 접근 금지. 시간은 인자로 받는다(`nowMs`).

## goal-3 (승패와 화면 전환) — 수용 기준 18~26
**완료 조건 (R2_decisions G절, 원문 그대로):**
> 타이틀에서 Enter로 시작해 모두 모으면 점수가 있는 클리어 화면이, 거미에게 잡히거나 시간이 다 되면 이유가 있는 실패 화면이 뜨고, Enter로 다시 하거나 타이틀로 돌아간다. (수용 기준 18~26)

### 규칙
- 화면 4개: `title` / `play` / `clear` / `fail`.
- 타이틀: 게임 이름 + "Enter 키로 시작" → Enter → 플레이(수용 18).
- 클리어: 이슬방울 8개 전부 수집 시(수용 19). "클리어!" + 점수 표시(수용 20).
- 점수 = 이슬방울 개수 × 100 + 클리어 시점 남은 시간의 **정수 초(내림)** × 10. 실패는 0점(확정 D·A절).
- 실패 이유 두 가지: 거미 접촉 → "거미에게 잡혔어요", 시간 0 → "밤이 끝났어요"(수용 21·22).

- 모든 화면 글자는 같은 한 가지 서체(`monospace`)로 읽힌다(수용 26).
- **모든 UI 문구는 src/strings.js 한 곳에만 둔다.**

## Escalation / Risk Gate
- **실행 정책 (사용자 합의)**: 품질 게이트는 **goal당 1회만** 시도한다(리뷰 1회 → 그 리뷰 해시로 체크포인트 1회). 실패하면 반복하지 않고 **실제 상태를 사실대로 기록**한 뒤 다음 goal로 넘어간다.
- **이 계획의 리뷰 반복**: 최대 2회.
- **중단 기준**: 한 goal에서 같은 시도를 6번 넘게 반복하지 않는다(AGENTS.md). 막히면 멈추고 어디서 막혔는지 보고한다 → 다음은 ralplan의 일.
- **에스컬레이션**: 기획서 값과 구현이 충돌하면 코드가 아니라 기획서를 먼저 고치고 사람에게 보여준다. 사람 확인 없이 숫자를 바꾸지 않는다.
